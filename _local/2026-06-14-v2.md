## Problem

Maintainer and Fork User sometimes disagree → unmerged PRs. Fork User wants both
(up-to-date official release) + (their custom features/bugfixes). Existing
trade-off: official release loses patches; forked release loses upstream updates.

## Solution

A workflow + tooling where **patches are intent, not diffs**, and an AI agent
re-realizes that intent against every upstream release.

**Core invariant: intent is truth, diffs are evidence.** Everything else follows.

- `.relay-patch` repo = permanent source of truth (intent files).
- `relay-patch/main` = derived release artifact (rebuilt on every re-derivation).
- Consumers update via `relay-patch update`, not raw `git pull`.

## Architecture

**Local-first.** The agent runs on the user's machine. No service required for v1.

| Layer | v1 | Future |
|---|---|---|
| AI agent | OpenCode (via slash-command skill) | Agent-agnostic via `@imbios/agent-sdk` (separate npm package, translation layer) |
| Orchestration | Local CLI + local scheduler | Optional GitHub Action on `.relay-patch`; optional hosted |
| Verification | Local (bun test, build commands) | Same; CI optional |
| Cost | User pays their agent | Same; hosted tier = future business model |

**Agent seam (design rule):** relay-patch never assumes a specific agent's API.
All agent invocation goes through one adapter interface:

```ts
interface AgentAdapter {
  realize(intent: Intent, base: Branch, context: DeriveContext): Promise<Realization>
  verify(realization: Realization, criteria: Acceptance[]): Promise<VerifyResult>
}
```

v1 ships one implementation: `OpenCodeAdapter`. When `@imbios/agent-sdk` exists,
swap the adapter — no other code changes. Do not leak OpenCode specifics into
orchestration, state management, or patch file handling.

## Repository layout — `USER/.relay-patch` or `ORG/.relay-patch`

One repo per user **or** per org. Personal patches live under the user's namespace;
shared team patches live under the org's namespace. Same schema, same tooling.

```
.relay-patch/
├── README.md                       auto-generated human-browsable index
├── global.json                     identity, default agent, schedule, token budget
└── repos/
    └── github.com/owner/repo/      namespaced by full host/owner/repo
        ├── upstream.json           upstream main SHA tracking, sync schedule
        ├── manifest.json           patch list, apply order, status, team fields
        └── patches/
            └── <patch-id>/
                ├── INTENT.md       source of truth (natural language)
                ├── ACCEPTANCE.md   machine-checkable criteria where possible
                ├── reference.diff  last successful realization (evidence only)
                ├── attempts.jsonl  append-only attempt history (FAILED + PASSED)
                └── tests/          optional runnable acceptance tests
```

Why `github.com/owner/repo` and not a slug:
- Disambiguates GitHub vs GitLab vs self-hosted.
- Survives same-name collisions across hosts.
- Mirrors a clone URL — zero ambiguity on import.

### Patch IDs

`<kebab-slug>-<ULID8>` — e.g. `dark-mode-toggle-01j6q3f8`.

- **Slug** = human-readable, may change as intent evolves.
- **ULID8** = forever-stable uniqueness, sortable by creation time.
- Renames update slug; ULID stays. Alias map in `manifest.json` tracks old slugs.
- Cross-user import never clashes.

Folder name = full ID. Title in `INTENT.md` frontmatter.

### `INTENT.md` frontmatter

```yaml
---
id: dark-mode-toggle-01j6q3f8
title: Add dark mode toggle in settings
target_repo: github.com/owner/repo
target_area: [src/settings/, src/theme/]
status: applied
applied_upstream_pr: none        # none | open(url, sha) | merged(sha, release) | closed(reason)
version: 2
license: MIT

# authorship (matters for org repos + Patch Directory import)
author: USERNAME
last_modified_by: USERNAME
owners: [USERNAME]               # who can mark satisfied / open upstream PRs
source_url: null                 # set when imported from another user
imported_at: null

created: 2026-06-13
last_realized_against_commit: abc123
verifies_with: bun test patches/dark-mode-toggle-01j6q3f8/tests/
---

## Intent
...

## Why
...

## Non-negotiables
...

## Implementation notes
...  (includes drift history — what upstream changed and how we adapted)
```

## Iteration model & attempt metadata

Both DRAFTING and RE-DERIVING are **indefinite iteration loops**. The user never
gets stuck — they retry until success. Every attempt (failed or passed) is
recorded to `attempts.jsonl`. This metadata serves three purposes:

1. **AI self-improvement** — on next attempt, the AI reads prior failures and
   avoids repeating them.
2. **Intent enrichment** — after success, the AI distills learnings from all
   attempts into INTENT.md's "Implementation constraints" and "Pitfalls" sections.
3. **Import transfer** — when user B imports the patch, they get the full attempt
   history. B's AI starts with A's accumulated knowledge → higher success rate.

### `attempts.jsonl` format

Append-only, one JSON object per line:

```jsonl
{"n":1,"phase":"drafting","timestamp":"2026-06-14T12:00:00Z","upstream_sha":"e93f0b1","approach":"Modified game.ts to add cheat parameter to generateSecret","result":"failed","failed_criteria":["game-ts-untouched"],"tokens":42000,"model":"glm-5.2"}
{"n":2,"phase":"drafting","timestamp":"2026-06-14T12:03:00Z","upstream_sha":"e93f0b1","approach":"Parsed --cheat from process.argv, printed secret before banner in index.ts only","result":"passed","tokens":38000,"model":"glm-5.2"}
{"n":3,"phase":"re-deriving","timestamp":"2026-06-14T18:00:00Z","upstream_sha":"cccad13","approach":"Tried to re-apply v1 diff via git apply","result":"failed","failed_criteria":["diff-does-not-apply"],"tokens":5000,"model":"glm-5.2","note":"reference.diff stale — context lines changed"}
{"n":4,"phase":"re-deriving","timestamp":"2026-06-14T18:02:00Z","upstream_sha":"cccad13","approach":"Re-derived from intent: piggybacked on v2 existing args parsing, added CHEAT const + conditional print","result":"passed","tokens":35000,"model":"glm-5.2"}
```

Fields:
- `n` — sequence number, starts at 1, monotonic
- `phase` — `drafting` | `re-deriving`
- `upstream_sha` — what upstream was the attempt against
- `approach` — short description of what the AI tried
- `result` — `passed` | `failed`
- `failed_criteria` — (failed only) which acceptance criteria failed
- `tokens` — token cost of this attempt
- `model` — which AI model was used
- `note` — optional context

### How attempts feed back into the AI prompt

On every new attempt, the orchestrator prepends prior attempts from
`attempts.jsonl` to the AI's prompt:

```
PRIOR ATTEMPTS FOR THIS PATCH (learn from these):
- Attempt 1 FAILED: "Modified game.ts to add cheat parameter" — violated: game-ts-untouched
  → DO NOT modify game.ts. The intent explicitly requires game.ts to stay untouched.
- Attempt 3 FAILED: "Re-apply v1 diff via git apply" — diff did not apply
  → DO NOT try to apply reference.diff mechanically. Re-derive from INTENT.md.

YOUR TASK: Re-derive this patch against the current upstream. Read INTENT.md for
what to do. Read reference.diff for what worked last time. Read the drift diff
for what changed. Produce a clean realization.
```

This is the mechanism that makes imported patches succeed: user B's AI inherits
user A's failure history and skips dead ends.

### INTENT.md enrichment after success

When a realization passes the gate, the orchestrator asks the AI to update
INTENT.md based on the full attempt history:

```markdown
## Implementation constraints (auto-enriched)
- DO NOT modify game.ts — failed in attempt 1
- DO NOT apply reference.diff mechanically — failed in attempt 3
- MUST piggyback on existing args parsing — worked in attempts 2, 4

## Pitfalls (from attempt history)
- v2.0.0 changed the import line (removed MIN, MAX; added DIFFICULTY_RANGES) —
  the cheat logic doesn't need MIN/MAX so this is safe
- v2.0.0 already has `const args = process.argv.slice(2)` — don't duplicate it
```

This section grows over time. Each drift cycle can add new pitfalls. This is what
makes the patch more robust with age rather than more fragile.

## Branch model

Two branch types do two different jobs. They diverge the moment you have 2+ patches.

| | `*` | `relay-patch/<patch-id>` |
|---|---|---|
| **Audience** | Maintainer (PR reviewer) | You / your team (your fork) |
| **Base** | Clean `upstream/main` | `relay-patch/main` (all patches applied) |
| **Contains** | One patch, no siblings | One patch + all siblings as context |
| **Purpose** | PR candidate to original repo | Internal workspace for realizing one patch on the cumulative base |
| **Lifespan** | One intent iteration; kept while PR is open | Reused on every re-derivation |

### Concrete example — adding dark mode when you already have fix-login applied

**Step 1 — `/relay-patch "add dark mode"`**

```
upstream/main
    │
    └── *       ← AI implements dark mode here
                 (base = clean upstream, no fix-login)
```

You test on `*`. It has upstream + dark mode only.

**Step 2 — `/relay-patch satisfied`**

AI writes intent to `.relay-patch`, then ports:

```
upstream/main
    │
    ├── *                               (kept — PR candidate)
    │
relay-patch/main
    │  (= upstream + fix-login)
    │
    └── relay-patch/dark-mode-01j6q3f8   ← PORT the diff here
                                          (base = relay-patch/main)
                                          │
                                          └──► merge → relay-patch/main
```

Now `relay-patch/main` = upstream + fix-login + dark-mode.

**Step 3 (optional) — open PR upstream**

PR from `*` → `owner/repo#main`. Clean diff — only dark mode, no fix-login noise.

**Step 4 — upstream releases v2, dark-mode drifts**

Orchestrator re-derives on `relay-patch/dark-mode-01j6q3f8` (off current
`relay-patch/main` + new upstream). AI works knowing fix-login is present.

### Implement once, port — NOT double work

```
/relay-patch INTENT
      │
      ▼
 AI implements on `*`        ← the ONLY creative work
      │
 user tests on `*`
      │
/relay-patch satisfied
      │
      ├──► port diff → relay-patch/main   (mechanical; AI only helps if
      │                                     sibling patches interfere)
      │
      └──► (optional) PR from `*` → upstream
```

Fresh re-implementation only happens during **drift re-derivation** (upstream
changed → AI re-derives from intent). That's a separate scheduled event, not
part of the initial satisfied flow.

## History model

**`relay-patch/main` is a release artifact, not a collaboration branch.**

It is rebuilt from scratch on every re-derivation: `upstream/main` + apply all
patches fresh. Force-pushed (or re-tagged). Consumers never `git pull` it directly.

### Why not fast-forward-only (the flaw I missed in chat)

Fast-forward-only means `relay-patch/main` accumulates patch commits on top of
upstream. When upstream advances and touches the same files those patch commits
modified, `git merge upstream/main` **conflicts on every drifted patch, every
release, forever.** The "resolution" is manual re-derivation dressed up as merge
conflict resolution — strictly worse than purpose-built re-derivation.

There is no sound way to keep patches as permanent commits on a branch that also
tracks upstream, when upstream changes the patched files. The patches are
derived; they must be re-derivable. Force-push accepts this honestly.

### Consumer update mechanism

Consumers never raw-`git pull` `relay-patch/main`. They run:

```bash
relay-patch update
```

Which does:
1. Fetch latest tag from `.relay-patch` (each successful re-derivation tags
   `relay-patch/main` as `v<upstream-tag>-rp<build>`).
2. Stash any local changes in the working tree.
3. Checkout the new tag.
4. Re-apply stashed changes (report conflicts if any).
5. Run build/install.

Tags mark known-good, post-verification-gate states. Rollback =
`relay-patch update --tag <previous>`. No git knowledge required from the user.

### Where history lives instead

Patch evolution history lives in **`.relay-patch` git history** (intent changes,
authorship, drift reports as commits to INTENT.md). That's the collaboration
surface. `relay-patch/main` is just "the current build."

## Patch lifecycle — state machine

```
                            /relay-patch INTENT
                                     │
                                     ▼
                              ┌─────────────┐
                              │   DRAFTING  │◄────┐
                              │ (branch: *) │     │ /relay-patch INTENT
                              │ AI implements│    │ (iterate, same intent)
                              │ user tries  │     │
                              └─────┬───────┘     │
                          satisfied?├──no─────────┘
                                    │ yes
                                    ▼
                              ┌─────────────┐  user opens PR upstream
                              │   APPLIED   │──────────────┐
                              │ ported to   │              │
                              │ relay-      │              ▼
                              │ patch/main  │       (attribute only:
                              └─────┬───────┘        applied_upstream_pr)
                    upstream drift │
                           detected│
                                    ▼
                              ┌─────────────┐
                              │   DRIFTED   │
                              └─────┬───────┘
                                    │ scheduled
                                    ▼
                              ┌─────────────┐
                              │ RE-DERIVING │
                              │ (relay-     │
                              │  patch/<id>)│
                              └─────┬───────┘
                       verify gate │
                  ┌────────────────┼────────────────┐
                  ▼                ▼                ▼
            ┌──────────┐    ┌─────────────┐  ┌────────┐
            │ APPLIED  │    │ NEEDS_HUMAN │  │UPSTREAM│
            │ (re-     │    │ (blocked)   │  │_ED     │
            │  applied)│    └──────┬──────┘  └───┬────┘
            └──────────┘           │ user fixes    │
                                   └───────────────┼──────┘
                                                   ▼
                                             ┌──────────┐
                                             │ RETIRED  │
                                             └──────────┘
```

### States

| State | Meaning | Who acts |
|---|---|---|
| **DRAFTING** | `*` branch open, AI implementing, user testing. Intent not yet committed to `.relay-patch`. | User + AI |
| **APPLIED** | Intent in `.relay-patch`; realization merged into `relay-patch/main`. `last_realized_against_commit` recorded. | Orchestrator |
| **DRIFTED** | Upstream advanced past recorded commit AND `target_area` has changes. Passive flag. | System |
| **RE-DERIVING** | AI running in `relay-patch/<patch-id>` against new upstream + siblings. | AI |
| **NEEDS_HUMAN** | Verification gate failed, 3 retries exhausted. **Blocks `relay-patch/main` rebuild for this patch only** (other patches can still advance; the blocked one uses its last good realization as fallback). | User |
| **UPSTREAMED** | Upstream now natively satisfies intent. | AI |
| **RETIRED** | Kept for history/sharing; no longer applied. | System |

### PR-to-upstream is an attribute, not a state

Patch stays APPLIED regardless of PR outcome. `applied_upstream_pr` transitions:

```
none ──(user opens PR from *)──► open(url, sha)
                                  │
              ┌───────────────────┴────────────┐
              ▼                                ▼
        merged(sha, release)            closed(reason)
              │                                │
              │                                └─► stays APPLIED (patch lives on)
              ▼
        triggers UPSTREAMED on next re-derivation
```

UPSTREAMED triggers from either:
1. `applied_upstream_pr = merged(...)`, or
2. AI semantic check detects intent natively satisfied upstream (independent
   implementation by maintainer).

### Transitions

| From → To | Trigger | Actor |
|---|---|---|
| DRAFTING → DRAFTING | `/relay-patch INTENT` (iterate) | User |
| DRAFTING → APPLIED | `/relay-patch satisfied` (ports to `relay-patch/main`) | User |
| APPLIED → DRIFTED | scheduled poll: upstream advanced AND `target_area` has diffs | System |
| DRIFTED → RE-DERIVING | scheduled re-derive tick (respects token budget) | System |
| RE-DERIVING → APPLIED | verification gate green | AI |
| RE-DERIVING → NEEDS_HUMAN | gate red, 3 retries exhausted | AI |
| RE-DERIVING → UPSTREAMED | AI detects intent satisfied upstream | AI |
| NEEDS_HUMAN → DRAFTING | user invokes `/relay-patch <id>` to fix | User |
| UPSTREAMED → RETIRED | confirmed stable upstream for N releases | System |

## The `DRIFTED → RE-DERIVED` AI contract

### Inputs

1. **Intent file** — what user wants, why, acceptance criteria, drift history.
2. **Previous realization** (`reference.diff`) — explicitly "reference, not truth."
3. **Previous upstream baseline SHA** — so AI can run
   `git log <baseline>..upstream/main -- <target_area>` and see exactly what
   changed in the relevant area.
4. **Target codebase** — fresh `relay-patch/main` (with siblings) in
   `relay-patch/<patch-id>`.
5. **Sibling context** — other APPLIED patches' realizations.
6. **Verification commands** — from INTENT.md frontmatter.

### Outputs

1. **New realization** — clean commits on `relay-patch/<patch-id>`.
2. **Drift report** — what upstream changed, whether approach diverged and why.
3. **Self-evaluation** — pass/fail per acceptance criterion.
4. **Confidence + `needs_human` flag.**

### Verification gate (all green to promote to APPLIED)

```
✓ Build succeeds
✓ Tests pass (patch's tests/ if defined, else repo default suite)
✓ AI self-eval: every acceptance criterion = pass (no "unknown" for auto-promote)
✓ Diff sanity: non-trivial vs upstream, not catastrophically large
✓ (optional) Idempotency: re-run produces same realization
```

**Failure policy:** never auto-ship yellow. "Unknown" or 3 failed retries →
NEEDS_HUMAN. The orchestrator (not the AI) updates
`last_realized_against_commit` only after the gate passes.

### Three failure modes that determine trust

1. **Upstream deleted what patch relied on.** AI re-targets or proposes RETIRED.
   Surface to user — never auto-re-target silently.
2. **Upstream independently implemented same intent.** AI detects via semantic
   similarity → UPSTREAMED. The happy failure.
3. **AI confident but wrong.** Mitigations: idempotency check, diff-size sanity,
   strict acceptance-criterion evaluation, and the rule that AI never updates
   `last_realized_against_commit`.

## Patch discovery & reuse (Patch Directory)

`.relay-patch` is public → browsing = GitHub search today, aggregator site later.
Model parallels [skills.sh](https://www.skills.sh/) and the `skills` CLI:
patches are to source repos what skills are to AI agents.

### Import flow

```bash
relay-patch import https://github.com/ALICE/.relay-patch/blob/main/repos/\
github.com/owner/repo/patches/dark-mode-toggle-01j6q3f8/INTENT.md
```

1. Fetch INTENT.md + ACCEPTANCE.md + tests/.
2. Copy into your `.relay-patch` under same `<patch-id>`.
3. Preserve `author: ALICE`, set `source_url`, `imported_at`.
4. AI re-derives `reference.diff` against your repo's `target_area`.
5. If `<patch-id>` exists locally: refuse without `--force` (treats as update).

### Cross-repo adaptation

Importing to a different repo than the author's → AI re-derives purely from
intent; `reference.diff` is hints only. A well-written intent adapts across
repos. This is where "intent is truth" pays off.

### Updates from original author

- Author bumps `version` in INTENT.md, pushes to their `.relay-patch`.
- Subscribers see via git history of `source_url`.
- Subscriber decides when to pull update + re-trigger re-derivation.
- Versioning = simple integer bumps.

### Licensing

Patches are creative work. Default MIT; per-patch override in frontmatter.
Import preserves original license and attribution — never strip.

## Cost UX (user-pays, must be first-class)

The user pays for their agent's tokens. Cost control is not a feature, it's a
prerequisite for trust.

### `target_area` skip — the default, not an optimization

Most upstream releases don't touch a given patch's area. Before any AI
invocation, the orchestrator runs:

```bash
git log <last_realized_against_commit>..upstream/main -- <target_area>
```

If empty → patch cannot have drifted → **skip re-derivation entirely, zero
tokens spent.** Update `last_realized_against_commit` and move on. This should
be the common path.

Only when the diff is non-empty does the patch enter DRIFTED → RE-DERIVING.

### Per-repo schedule

```json
// global.json
{
  "schedule": "on-upstream-release"  // | "daily" | "weekly" | "manual"
}
```

`on-upstream-release` = poll upstream tags/releases, trigger only on new release.
Default. Cheapest sensible option.

### Token budget cap

```json
{
  "token_budget_per_run": 500000,
  "on_budget_exceed": "pause"  // | "abort" | "continue-and-warn"
}
```

On exceed with `pause`: orchestrator prompts user mid-run:
"Spent 480k/500k tokens. 2 patches remain (est. 180k). Continue / pause / abort?"

### Cost history

Per-patch token usage logged to `.relay-patch/_cost/` (gitignored or committed,
user choice). User sees: "dark-mode-toggle averages 12k tokens/re-derivation,
re-derived 8 times." Makes cost predictable over time.

### Dry-run mode

```bash
relay-patch drift-check
```

Reports: which patches drifted, estimated cost per patch, total estimated cost,
whether budget allows. Runs zero AI. User decides whether to proceed.

## Scenarios

### Scenario 1 — PR merged upstream (normal)

1. Maintainer owns `owner/repo`, publishes from `main`.
2. User forks, clones.
3. `/relay-patch "add dark mode"` → AI opens `*` off `upstream/main`, implements.
4. User tests on `*`, iterates with `/relay-patch "..."`.
5. `/relay-patch satisfied`:
   - Intent → `.relay-patch`.
   - Diff ported to `relay-patch/main`.
6. User opens PR from `*` → `owner/repo#main`.
7. Maintainer merges.
8. Next scheduled poll: AI detects intent satisfied upstream → UPSTREAMED →
   RETIRED. `relay-patch/main` no longer carries this patch. User consumes
   upstream unmodified.

### Scenario 2 — PR rejected / not merged (relay-patch's reason to exist)

1. Maintainer owns `owner/repo`, publishes from `main`.
2. User forks, clones.
3. `/relay-patch "add dark mode"` → AI opens `*`, implements.
4. User iterates, `/relay-patch satisfied` → intent in `.relay-patch`, ported to
   `relay-patch/main`.
5. User opens PR from `*`; maintainer closes ("out of scope").
   - `applied_upstream_pr = closed("out of scope")`.
   - Patch stays APPLIED. User keeps `relay-patch/main`.
6. **Maintainer publishes v2.0.** Scheduled poll runs `target_area` check.
7. If dark-mode's `target_area` untouched by v2.0 → skip, update SHA, zero cost.
8. If touched → DRIFTED → RE-DERIVING (respects token budget):
   - Green → APPLIED. `relay-patch/main` rebuilt, new tag cut. User runs
     `relay-patch update`.
   - Red → NEEDS_HUMAN. User runs `/relay-patch dark-mode-toggle-01j6q3f8`.
9. Loop continues. User always has up-to-date upstream + their patch.

### Scenario 3 — Reusing someone else's patch

1. User B wants dark mode on same repo.
2. B browses `github.com/ALICE/.relay-patch`, finds `dark-mode-toggle-01j6q3f8`.
3. `relay-patch import <url>` → fetches, copies, preserves `author: ALICE`.
4. AI re-derives against B's fork.
5. B's `relay-patch/main` has dark mode — B wrote no intent.
6. On drift, A and B get independent re-derivations. Both stay true to ALICE's
   intent; realizations may differ if their forks differ.

### Scenario 4 — Org team workflow

1. `ORG/.relay-patch` is shared. Three engineers have push access.
2. Engineer A creates `dark-mode-toggle-01j6q3f8` (author: A).
3. Engineer B imports a patch from outside, improves the intent, bumps version
   (last_modified_by: B).
4. Engineer C runs `relay-patch update` on their local fork — gets A's and B's
   work via `relay-patch/main` rebuild.
5. `owners` field controls who can mark satisfied / open upstream PRs.
6. Same state machine; `author` and `last_modified_by` track who did what.

## Open questions (not blocking v1 implementation)

- **Multi-patch interaction.** If patch A and B both touch `theme.tsx`, does AI
  re-derive sequentially (A then B) or jointly? Start sequential; surface
  conflicts. Joint re-derivation = v2.
- **Apply order changes.** If A depends on B but manifest order is wrong? Detect
  via re-derivation failure, not static analysis.
- **AI determinism.** Same intent + same upstream should yield same realization.
  Idempotency check catches violations; flag for human.
- **NEEDS_HUMAN + partial rebuild.** If patch 3 of 5 is blocked, does
  `relay-patch/main` rebuild with patches 1, 2, 4, 5 + last-known-good of 3?
  Or block entirely? Current plan: rebuild with fallback for the blocked one,
  tag it `v<upstream>-rp<build>-partial`, surface loudly.
- **What if upstream deletes the entire `target_area`?** AI proposes RETIRED;
  user confirms. Never auto-retire.
- **Private upstreams.** `.relay-patch` is public — does intent leak info about
  private target repos? Document: don't put proprietary code in INTENT.md.
- **Agent-agnostic timing.** When does `@imbios/agent-sdk` become a real project?
  Hint: when a second agent adapter is needed. Don't build it speculatively.

---

## Non-goals (explicit)

- Not a replacement for `git rebase`. No general-purpose patch management.
- Not a CI system. Verification runs locally or via scheduled orchestrator, not
  on every push.
- Not multi-host in v1. GitHub only; design accommodates others.
- Not a package manager. Patches realize into source, not into `node_modules`.
- Not multi-agent in v1. OpenCode only. The adapter seam is the migration path.
